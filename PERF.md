# Performance regressions

Performance regressions is a tricky topic: the idea is to control most
parameters, and compare some specific aspects with a tolerance.

Each regression check uses a Student's t prediction interval, to check if the
latest measurement belongs to the distribution of the prior successful ones,
taking into account the uncertainty on their mean. A regression is reported
when the p-value is below `alpha` (0.05 by default, see the `--reg-alpha` option
to override it). At least 20 prior measurements are required by default, see the
`--reg-min-history` option.

When a test has multiple checks, their p-values are adjusted with the
Holm-Bonferroni method before being compared with `alpha`: without that, the more
checks, the more false positives. This can be disabled per test, with
`holm_bonferroni: false` in its `regression` section.

Results of each run are kept. The ones with a `skip` file are ignored by the
next regression checks: the file contains the reason.

## Deployment

Two modes are currently supported: virtual only, with physical network cards.

### Virtual only

This mode is ideal for the developments and easy to deploy tests. The drawbacks
are that using virtual NIC, e.g. the way the SKB are allocated are completely
different, especially on the reception part.

```
 ----------------------------------------------
|  --------                          --------  |
| |        |                        |        | |
| |  VM 1  | ------- bridge ------- |  VM 2  | |
| |        |  netem          netem  |        | |
|  --------                          --------  |
|                   Container                  |
 ----------------------------------------------
```

### With physical network cards

In order to simulate more real network conditions, it is recommended to use a
minimum of 2 machines, each with 2 Ethernet ports:

- one running 2 VMs: sender and receiver
- one in charge of the shaping

It is better to avoid using TC for the shaping on the interfaces used by the
sender or receiver because this will use different paths from the "normal"
behaviour on the kernel side.

```
 ---------------------------
|  -----------------------  |    ------------------------
| |  --------             | |   |         Netem          |
| | |        | --- Eth 1 ---------- Eth 1 ---            |
| | |  VM 1  |            | |   |            |           |
| | |        |            | |   |            B           |
| |  --------             | |   |            R           |
| |                       | |   |            I           |
| |         Host 1        | |   |            D   Host 2  |
| |                       | |   |            G           |
| |  --------             | |   |            E           |
| | |        |            | |   |            |           |
| | |  VM 2  |            | |   |            /           |
| | |        | --- Eth 2 ---------- Eth 2 --             |
| |  --------             | |   |         Netem          |
| |       Container       | |    ------------------------
| |      --net=host       | |
|  -----------------------  |
 ---------------------------
```

## Network conditions

Each bridge described in the YAML file is shaped with `netem` on all its ports,
so in both directions: `delay_ms` is then half of the added RTT.

When `rate_mbit` is set, the queue size is computed from `max_latency_ms`: the
one-way delay, including the maximum queuing delay. By default, it is set to
twice `delay_ms`, meaning the queue can hold up to `delay_ms` of traffic. The
queue size, including the packets in the delay line, is limited to a minimum of
10 packets. It can be forced with `limit_pkts`.

## Run

The Docker image described in [README.md](README.md) can be used. To get more
details, see:

```shell
docker run (...) perf-normal -h
```

Tests in the `perf` directory using a `.jsonnet` source file are generated by
`perf/gen.sh`: do not modify the generated `.yml` files.

## Tracking regressions locally

Regressions are only checked when a regression directory is given with
`--reg-dir`: this is done automatically in the CI. Results are stored there per
test, in `<suite>/<test>/<run id>`, and kept between runs.

Before checking modifications, a history of results is needed: from a version
without these modifications, in the same environment (same idle machine, same
kernel config, same tests).

- From the kernel source directory, define a helper:

  ```shell
  perf_run() {
      docker run -v "${PWD}:${PWD}:rw" -w "${PWD}" -v "${PWD}/.home:/root:rw" \
             --rm --privileged mptcp/mptcp-upstream-virtme-docker:latest \
             perf-normal --reg-dir .virtme/perf_reg "${@}"
  }
  ```

  Or if you have the `.virtme*.sh` scripts:

  ```shell
  alias perf_run="./.virtme.sh perf-normal --reg-dir .virtme/perf_reg"
  ```

- Switch to a version without the modifications, build the kernel once with
  `--build-only`, then execute the tests multiple times, e.g. 5 times:

  ```shell
  git switch --detach <base>

  # to start a new history
  rm -rf .virtme/perf_reg
  mkdir -p .virtme/perf_reg

  perf_run --build-only
  for i in $(seq 5); do
      perf_run -C /perf  # the test suite is long: check that before submission
                         # for dev, use -c, e.g. -c /perf/sched-baseline.yml
  done
  ```

  **Note**: run more if there were errors

- Switch to the version with the modifications, build the kernel again, and
  execute the same tests with:
  - `--reg-min-history 5`: compare with the 5 previous runs, instead of 20 by
    default.
  - `--reg-alpha 0.01`: use a lower significance level to only report the most
    obvious regressions, or a higher one to be stricter. Default: 0.05.
  - `--reg-exclude`: keep the results, but not use them for the next regression
    checks. These tests can then be executed again after new modifications,
    still compared with the same history.

  ```shell
  git switch <branch>
  perf_run --build-only
  perf_run -C /perf --reg-min-history 5 --reg-alpha 0.01 --reg-exclude
           # or with -c /perf/<test>
  ```

  **Note**: it might be interesting to launch the last command on the base
  to find out which tests produce unstable results, especially when the sample
  is small.

Regressions are reported in the summary, and in the `regs.txt` file of each
test. Improvements are in the `improvement.txt` file of each test, and in the
comment of the JSON results.

**Note**: more runs in the history -- e.g. 20 by default -- give more reliable
comparisons, fewer false positives.

## Adapting the regressions

Changing the regression parameters can be needed, but can also have an impact on
the results. When the behaviour has changed, it might be required to skip old
ones.

To only check the regressions again, re-using the results of the previous run,
e.g. after modifying the regression checks or their parameters, add
`--reg-only` with the same options as before: the tests are not executed, and
the previous results are kept.

```shell
perf_run -C /perf --reg-min-history 5 --reg-alpha 0.01 --reg-only
```

Similarly, to also validate the results again, e.g. after modifying the
validation checks or the dstat offsets, use `--validation-only` instead: the
dstat files are parsed again, the validation scripts are executed on the
previous results, then the regressions are checked. Note that the results from
the history are not modified, e.g. with the new dstat offsets. This needs the
dstat time window saved by recent runs: older ones need a full run.

After an accepted change in behaviour, the new results would always be marked
as regressions, and then excluded from the history. To restart the history from
the latest results of each checked test, add `--reg-reset`, alone or with
`--reg-only` to use the results from the previous run. The regression checks
will then be done again once enough new measurements are available, see
`--reg-min-history`.
