# Performance regressions

Performance regressions is a tricky topic: the idea is to control most
parameters, and compare some specific aspects with a tolerance.

Each regression check uses Student's t-test to compare the mean of prior
successful measurements against the latest measurement. A regression is reported
when the p-value is below `alpha`. At least 20 prior measurements are required
by default, see the `--reg-min-history` option.

## Deployment

Two modes are currently supported: virtual only, with physical network cards.

### Virtual only

This mode is ideal for the developments and easy to deploy tests. The drawbacks
are that using virtual NIC, e.g. the way the SKB are allocated are completely
different, especially on the reception part.

```
 ----------------------------------------------
|  --------                          --------  |
| |        |                        |        | |
| |  VM 1  | ------- bridge ------- |  VM 2  | |
| |        |  netem          netem  |        | |
|  --------                          --------  |
|                   Container                  |
 ----------------------------------------------
```

### With physical network cards

In order to simulate more real network conditions, it is recommended to use a
minimum of 2 machines, each with 2 Ethernet ports:

- one running 2 VMs: sender and receiver
- one in charge of the shaping

It is better to avoid using TC for the shaping on the interfaces used by the
sender or receiver because this will use different paths from the "normal"
behaviour on the kernel side.

```
 ---------------------------
|  -----------------------  |    ------------------------
| |  --------             | |   |         Netem          |
| | |        | --- Eth 1 ---------- Eth 1 ---            |
| | |  VM 1  |            | |   |            |           |
| | |        |            | |   |            B           |
| |  --------             | |   |            R           |
| |                       | |   |            I           |
| |         Host 1        | |   |            D   Host 2  |
| |                       | |   |            G           |
| |  --------             | |   |            E           |
| | |        |            | |   |            |           |
| | |  VM 2  |            | |   |            /           |
| | |        | --- Eth 2 ---------- Eth 2 --             |
| |  --------             | |   |         Netem          |
| |       Container       | |    ------------------------
| |      --net=host       | |
|  -----------------------  |
 ---------------------------
```

## Network conditions

Each bridge described in the YAML file is shaped with `netem` on all its ports,
so in both directions: `delay_ms` is then half of the added RTT.

When `rate_mbit` is set, the queue size is computed from `max_latency_ms`: the
one-way delay, including the maximum queuing delay. By default, it is set to
twice `delay_ms`, meaning the queue can hold up to `delay_ms` of traffic. The
queue size, including the packets in the delay line, is limited to a minimum of
10 packets. It can be forced with `limit_pkts`.

## Run

The Docker image described in [README.md](README.md) can be used. To get more
details, see:

```shell
docker run (...) perf-normal -h
```

Tests in the `perf` directory using a `.jsonnet` source file are generated by
`perf/gen.sh`: do not modify the generated `.yml` files.
